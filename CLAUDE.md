## Project Overview

MuMu Camera is a distributed WebRTC-based camera streaming system. The central server handles signaling only — all video flows peer-to-peer through WebRTC (with TURN fallback). The system is designed for Raspberry Pi camera streaming with features like PTZ control, GPS tracking, and recording playback.

## Architecture

```
Device Agent (Raspberry Pi)  ←─ WebSocket signaling ─→  Backend (FastAPI)
         ↕                                                    ↕
    WebRTC P2P video                                  WebSocket signaling
         ↕                                                    ↕
                              Web Client (Browser)
```

**Components:**
- **Backend** (`backend/`): FastAPI signaling server. Single-file app in `backend/app/main.py` (~1095 lines). Handles auth (JWT+bcrypt), device management, WebSocket signaling for both devices and viewers, HTTP proxy to device APIs, and HLS recording streaming. Uses SQLAlchemy async ORM with PostgreSQL, Redis for presence/session tracking.
- **Device Agent** (`device-agent/`): Python agent running on camera devices. Main class `Go2RTCProxyAgent` in `agent.py`. Connects to backend via WebSocket, proxies HTTP requests to go2rtc (port 1984), supports ONVIF PTZ, GPS data, recording management. Includes utilities: `pair.py`, `recorder.py`, `indexer.py`, `cleaner.py`, `gps_reader.py`, `onvif_controller.py`.
- **Web Client** (`web/`): Vanilla HTML/CSS/JS, no build step. Key files: `app.js` (device management/pairing), `webrtc.js` (peer connections), `recordings.js` (playback/timeline). Entry pages: `login.html`, `index.html`, `recordings.html`.
- **Infrastructure**: PostgreSQL 15, Redis 7, Coturn (TURN/STUN), Nginx reverse proxy.

**Database tables** (via Alembic): Users, Devices, DeviceOwnership, DeviceToken, PairingCode, WatchSession.

**WebSocket endpoints**: `/ws/device` (device agents), `/ws/viewer` (browser clients).

## Common Commands

### Start all services
```bash
docker-compose up -d
docker-compose exec backend alembic upgrade head
```

### Start with device simulator (no hardware needed)
```bash
docker-compose --profile sim up -d
```

### Backend development (outside Docker)
```bash
cd backend
pip install -r requirements.txt
uvicorn app.main:app --reload
```

### Database migrations
```bash
cd backend
alembic revision --autogenerate -m "description"
alembic upgrade head
```

### Device agent development
```bash
cd device-agent
pip install -r requirements.txt
python agent.py --backend ws://localhost:8000/ws/device --device-id test-device-001
```

### Web client
No build step. Edit files in `web/` directly; Nginx serves them.

### View logs
```bash
docker-compose logs backend
docker-compose logs -f backend  # follow
```

### Access points
- Web UI: http://localhost:8080
- Backend API: http://localhost:8000
- API docs (Swagger): http://localhost:8000/docs

## Environment Configuration

Copy `.env.example` to `.env`. Key variables:
- `POSTGRES_PASSWORD`, `TURN_SECRET`, `JWT_SECRET` — must change for production
- `TURN_PUBLIC_HOST` — set to public IP/domain for non-local deployment
- `BACKEND_CORS_ORIGINS` — comma-separated allowed origins
- `WEB_PORT` — Nginx port (default 8080)

Backend config is in `backend/app/config.py` using Pydantic settings (loads from env vars).

## Key Technical Details

- Backend is a single large file (`main.py`) containing all routes, WebSocket handlers, and business logic
- No test suite or linting configuration exists in this project
- The project uses async Python throughout (asyncio, asyncpg, aiohttp)
- Device-to-backend communication uses WebSocket; backend proxies HTTP requests to devices for go2rtc API, recordings, and HLS segments
- TURN server uses dynamic credentials generated by the backend (shared secret with coturn)
- Pairing workflow: device generates a 6-digit code via `pair.py`, user enters it in web UI to link device to account
- Documentation is in Chinese (Traditional) in some files; code and API are in English
